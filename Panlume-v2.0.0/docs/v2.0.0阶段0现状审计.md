## 3. 现有模块与可复用能力

### 行情、存储与调度

- `pandeng/data/`：模拟、CSV/JSON 回放、受控适配器、清洗、质量记录、交易日历和调度。
- `pandeng/monitor/`：低频轮询、暂停恢复、断网补记和轮次状态。
- `pandeng/storage/db.py`：SQLite 连接、初始化、外键和事务边界。
- `pandeng/storage/schema.sql`：结构版本 6 的完整表结构。
- `pandeng/storage/repositories.py`、`pandeng/storage/monitor.py`：原始记录和调度持久化。

可复用点：原始分钟/日线均有数据库 ID、来源、确认状态、入库运行 ID 和原始 JSON；指标快照与规则检查也保留 ID，可作为事实包证据链，不需要另造数据来源。

### 指标、规则与持仓

- `pandeng/indicators/intraday.py`：分钟收益、MA、估算 VWAP、成交量比、日内高低点、板块相对表现及连续性门控。
- `pandeng/indicators/daily.py`：确认前复权日 K、MA20、拐头与正式双条件。
- `pandeng/analyzer/service.py`：把指标、分析运行、输入哈希和规则评价串起来。
- `pandeng/rules/engine.py`：快速涨跌、放量突破、低于 VWAP、逐批固定止损，以及事件合并、解除、冷却和提醒计数。
- `pandeng/holdings/positions.py`：人工确认批次与 T+1。

可复用点：规则结论已经确定性保存。`rule_events` 提供事件 ID、状态、首末触发、提醒次数和检查次数；`rule_event_checks` 提供逐次状态、通知类型和载荷。冷却截止时间可由 `last_reminded_at` 与现有优先级冷却配置计算，解除时间可由解除检查记录确定，不需要修改规则判断逻辑。

### 摘要、复盘与模型

- `pandeng/summarizer/content.py`：`SummaryFacts`、固定模板、提示词和严格数值/代码/时间/禁用表述校验。
- `pandeng/summarizer/service.py`：摘要任务、结果、回退原因和模型调用事务化存储。
- `pandeng/summarizer/worker.py`：有界队列、单工作线程、异常回退和关闭收尾。
- `pandeng/summarizer/ollama.py`：Ollama 非流式生成客户端、响应上限和 R1 思考段分离。
- `pandeng/review/service.py`：只读汇总单票单日事实、稳定输入 JSON/SHA-256、双语固定复盘和幂等保存。
- `pandeng/desktop/summary.py`：观察页最新行情摘要及 Ollama 回退。

可复用点：已有严格校验、固定模板、回退原因、调用审计和稳定哈希机制。统一事实包应成为这些链路的共同输入适配层，而不是替换规则或重写存储。

| 分组 | 数据表 | 报告链路用途 |
| --- | --- | --- |
| 元数据与日志 | `app_metadata`、`run_logs` | 结构版本和运行记录 |
| 原始行情与质量 | `ingestion_runs`、`data_quality_issues`、`minute_bars`、`daily_qfq_bars`、`trading_calendar`、`processing_checkpoints` | 数据范围、来源、确认、质量、证据 ID |
| 调度 | `monitor_state`、`monitor_code_states`、`monitor_rounds`、`monitor_events` | 获取过程、缺口和恢复上下文 |
| 持仓 | `position_lots`、`position_audit` | 仅使用已确认持仓和人工审计 |
| 分析与规则 | `analysis_runs`、`indicator_snapshots`、`rule_events`、`rule_event_checks`、`daily_analysis` | 指标、规则状态、时间线、输入哈希和追溯 |
| 摘要与模型 | `summary_tasks`、`summary_results`、`model_calls` | 固定模板、模型结果、校验与回退原因 |
| 复盘 | `review_runs`、`cloud_review_calls` | 历史复盘原文、输入事实和既有云端门控记录 |

迁移风险：

1. `Database.initialize()` 当前执行幂等建表后直接写入结构版本 6，不是通用的版本检查/逐版迁移框架。2.0 不能照搬这种方式覆盖旧库版本号。
2. 阶段 1 的事实包可以先在内存生成并稳定序列化，复用已有 ID 和 `review_runs.input_json`，不要求新增表。
3. 阶段 2 的报告预设应放独立严格 JSON，不把新键塞进旧设置文件，也不把预设写入 SQLite。
4. 若后续确需新持久化字段或表，必须单独设计显式结构版本 7 迁移：先备份、检查当前版本、事务迁移、失败恢复，再验收；不得直接覆盖 v1 数据库。
5. 历史 `summary_results.text`、`review_runs.local_report/input_json`、告警和原始 JSON 均保持原文，不做批量重写。

## 5. 当前报告链路与差距

### 实时事件摘要

当前链路：

```text
AnalysisService
  → indicator_snapshots / analysis_runs
  → RuleEngine
  → rule_events / rule_event_checks
  → SummaryFacts（仅 live 且实际通知）
  → 固定模板或 Ollama
  → validate_summary
  → summary_tasks / summary_results / model_calls
  → 桌面“事件与摘要”
```

已有保护：只有实际 live 提醒可建摘要任务；代码、完整时间、关键数值、异常标签、交易指令及部分无依据原因/预测会校验，失败保留完整固定模板。

差距：`SummaryFacts` 只覆盖当前检查和载荷，不是统一事实包；缺少完整数据范围、来源记录、质量摘要、事件首末状态、解除时间、合并/冷却明细、时间线和统一追溯结构。默认摘要上限为 400 字，当前模板偏短。

### 单票本地复盘

当前链路：

```text
_review_input 只读查询
  → 普通 dict 事实
  → input_json + SHA-256
  → _local_report 固定模板
  → review_runs
  → 桌面“本地复盘”
```

已有保护：输入稳定序列化、幂等读取、原文保存、默认无模型/云端调用。

差距：报告只有计数、最新快照、事件最新文本和日线结论；缺少完整价量统计、逐时变化、逐次规则计算依据、解除/冷却状态、缺失数据的统一限制区和可直接导出的统一事实包。它可作为详细分析的事实来源，但应迁入共同事实包构建器。

### 观察页摘要

当前链路独立读取最多 5 只股票的最新分钟，只检查模型文本非空和长度，没有走 `validate_summary`。

差距：这是第三条独立报告路径，且模型校验弱于事件摘要。2.0 应让新报告功能走统一事实包和统一校验；旧页面可适配调用，不应继续扩张这条独立事实组织逻辑。

## 6. 桌面页面与零终端差距

现有 10 个页面：

1. 总览；
2. 观察设置（模拟观察、受控真实短验收、添加/删除股票）；
3. 本地复盘；
4. 数据体检；
5. 事件与摘要；
6. 模型与输出；
7. 语言；
8. 数据管理（备份、清理、打开数据目录）；
9. 离线演示；
10. 关于。

可复用桌面能力：后台线程、任务名去重、主线程 UI 队列、错误日志、活动任务关闭保护、独立演示库、备份/清理、语言重启生效和受控真实请求确认。

主要差距：

- 没有报告生成/事实包预览/JSON 与 Markdown 导出页面，也没有报告预设。
- 桌面设置限制 1～5 只股票，摘要又截取前 5 只；YAML 配置本身已允许 1～10 只。
- 观察对象只有代码和名称，没有启停状态及图形化顺序调整。
- 模型页固定 `deepseek-r1:14b`，连接地址写死为 `127.0.0.1:11434`，健康检查仅读取 `/api/tags` 的名称。
- 没有模型参数规模识别、推荐等级覆盖、模型大小、下载进度、取消或正式 API 删除能力。
- 核心后台任务已有保护，但新增下载等长任务必须纳入同一活动任务/关闭机制，UI 回调仍回主线程。

## 7. 高 DPI 与滚动审计

- `main()` 直接创建 `tk.Tk()`，之前没有 DPI 感知入口。
- PyInstaller spec 和 Inno Setup 当前未设置 DPI manifest；后续应只保留一个明确入口，并在根窗口创建前完成。
- 没有显式 Tk scaling 初始化、多显示器 DPI 变化处理或缩放级别验收。
- `ScrollablePage` 已按区域滚动并保留 Text/Treeview 自身行为，但 `show_page()` 每次都会遍历绑定，`after_idle` 没有统一登记和取消。
- 画布尺寸变化时会遍历所有后代更新换行宽度；长报告阶段需要避免滚动或刷新时重建整页控件。
- 当前自动测试覆盖小窗口导航和部分滚动行为，但不能替代 100%～200%、多 DPI 显示器、1080p/2K 的 Windows 人工验收。

## 8. 配置、语言与构建现状

- 桌面设置使用严格 JSON 和原子替换，未知键会报错；新预设必须独立版本化，避免旧程序无法读取。
- 新安装通过 `main(... default_language="en")` 默认英文；已有缺 `language` 的设置走中文默认值，需保留此差异。
- 语言集中于 `pandeng/desktop/i18n.py`，目前支持 `zh-CN`、`en`；新增报告页面必须集中翻译。
- PyInstaller 为 onedir、windowed、无 UPX，资源包含 schema、演示配置和图标。
- Inno Setup 为当前用户安装，标准卸载默认保留个人数据。
- 版本号分散在 `pandeng/desktop/__init__.py`、`packaging/Panlume.iss`、两个构建脚本和发布文档中；只有阶段 8 全部必需验收通过后才能统一改为 2.0.0。

## 10. 阶段 1 实施约束

1. 先定义版本化、稳定 JSON 的事实包，再让两类报告共用；运行时间戳不进入内容哈希。
2. 从现有数据库记录构建证据，不重算规则，不让模型计算指标。
3. 实时报告保留现有任务和严格回退链；详细报告无 Ollama 时必须有完整程序事实区。
4. 条件表达式由规则 ID 的确定性描述和已保存载荷组成；不能凭自然语言猜造阈值。
5. 覆盖无事件、数据缺失、预热不足、事件解除、重复合并、冷却、固定止损持仓上下文和中英文。
6. 先新增聚焦测试并运行，再跑完整 400+ 测试；不得删除断言、放宽既有校验或跳过失败用例。
