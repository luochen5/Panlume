# 第三阶段收尾记录

记录日期：2026-11-17

## 一、固定止损等号边界

第三阶段最终采用“触及或跌破即提醒”：目标分钟收盘价小于或等于该有效持仓批次的人工确认止损价时触发，即 `close <= stop_loss_price`。

边界行为固定如下：

- 收盘价高于止损价：不触发；已有活动事件在此时解除。
- 收盘价等于止损价：触发。
- 收盘价低于止损价：触发。
- 解除后再次等于或低于止损价：创建新的活动事件，并立即产生首次提醒。
- 持续触发期间仍按高优先级独立间隔重复提醒，不逐轮刷屏。

止损提醒只保存风险记录，不执行交易。T＋1 日历不完整只使可卖数量保持未知，不改变价格线判定。

## 二、历史分钟缺口与固定止损解耦

固定止损只依赖目标时刻那一根已确认分钟线的收盘价，以及用户人工确认的有效持仓批次。早期分钟存在缺口时，只要目标分钟存在、时间完全匹配且已确认，仍可进行固定止损判断，并保存数据质量警告。

历史缺口、额外分钟或历史分钟未确认会使依赖完整当日序列的指标保持未知，包括收益率、分钟均线、日内高低点、典型价估算 VWAP、放量突破所需此前高点、当日开盘以来收益和相对板块表现。已有普通活动事件收到未知检查，不会被误解除。

以下情形不开放新的价格线判定：目标分钟缺失、目标分钟未确认、时间无法与本轮目标完全匹配，或本轮数据清洗、重复内容冲突等质量异常使当前行情不可信。已有活动事件保持活动并记录未知，不得写成“无触发”。

调度器继续保留逐股票连续检查点。存在历史缺口时，可以开放当前分钟的止损分析，但连续检查点仍停留在缺口之前；后续补数仍按原缺口区间执行。恢复与回放只写补记，不产生当时实时提醒。

## 三、持仓减仓与更正

本阶段不直接修改 SQLite 中的持仓数量、买入日期或止损价，也不提供无审计的覆盖更新。

部分卖出时，先使用 `holdings list` 核对批次，再使用 `holdings archive` 归档原批次，原因中写明实际人工核对情况和原批次编号；如仍有剩余记录数量，再使用 `holdings add` 新增剩余批次，买入日期沿用人工核对后的原买入日期，止损价由用户重新确认。新增和归档都会追加 `position_audit`。

录入错误时同样采用“归档错误批次并新增核对后的批次”。这会形成新的批次编号，旧记录永久保留。T＋1 按新记录中的人工确认买入日期和明确交易日历计算。该流程只维护个人研究记录，不代表账户查询或实际交易。

`holdings reduce` 和 `holdings correct` 暂不在第三阶段加入，避免在口径收尾时扩张命令面；后续如实现，必须继续保持精确人工确认和追加审计。

## 四、功能范围

MA20、拐头、日 K 单向确认、恢复补记、事件合并和提醒生命周期沿用已经验收的实现。桌面窗口、Logo、EXE、安全更新、备份恢复、一键卸载、GitHub 发布和杀毒误报验证均属于远期工程化功能，不进入第四阶段 A。

第四阶段 A 仅增加 Ollama 异步摘要及配套安全能力：R1 思考段与最终摘要分离、输出校验、固定模板回退、有界队列、单模型工作线程、SQLite 跨线程连接隔离、有限退出、异常退出后的任务恢复，以及结构版本 4 到 5 的数据库副本升级测试。摘要只设置合理长度上限，不要求凑足 150 字。

## 五、验收要求

收尾代码必须留下独立测试名称，覆盖高于、等于、低于、解除、再次触及的完整止损边界，以及“历史分钟缺失但当前分钟有效且触及止损价仍触发”。之后运行全量离线回归，再进入第四阶段 A 的模型测试；离线测试不得请求真实 Ollama 或云端服务。
